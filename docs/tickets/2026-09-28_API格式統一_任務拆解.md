# API 格式統一 任務拆解

來源：`Truku_backend/說明文件/前端交接/2026-09-28_加急_API格式統一.md`（SCAN-A01、SCAN-A03、BUG-16）。行號以 `fix/review-followups` 分支為準，與交接文件引用的 master 行號略有偏移。

## 現況與前提
- 技術棧：Flutter，所有請求走 `ApiClient`（`lib/core/network/api_client.dart`）。更新提示走 Firebase Remote Config（`lib/services/app_update/`）。
- 既有相關機制：
  - 分頁由各 service 自己組 query，沒有共用型別。「還有沒有下一頁」各畫面判斷方式不同：比 `total`（文化搜尋、文章／影音收藏按讚、測驗紀錄、我參加的活動）、比「這頁筆數 < pageSize」（活動收藏按讚）、看是否空頁（活動搜尋）、看 `next_cursor != null`（論壇、私訊、通知、小米幣）。
  - 游標式的 `next_cursor` 目前都解析成 `int`，只有論壇按讚清單已經是 `String?`。
  - 畫面上沒有任何地方顯示「共 N 筆」，拿掉 `total` 不影響 UI。
  - 更新提示：`latest_version_*` 只提醒、可略過，沒有最低版本。提示層 `AppUpdatePromptLayer` 疊在 Navigator 之上，連同意條款畫面也蓋得住。
- 這次會動到的既有部位：`lib/services/` 的 event／article／video／history／forum／friend／millet_service；`lib/models/` 的 forum_models／event_model／article_models／video_models／history_models／millet_transaction；各列表畫面；`app_update_service.dart`、`app_update_prompt.dart`、`terms_consent_screen.dart`；相關測試與 `test/fixtures/api/`。
- 已定案的技術前提：
  - 後端規格：`limit` 1–50、預設 20；`cursor` 原樣帶回 `page_info.next_cursor`（字串，不解析、不自組）；`has_more == false` 就停止載入；位移式端點（活動、文章、影音、測驗紀錄）依 `id` 去重。論壇下拉刷新的 `after` 不在這次範圍。
  - 後端新格式已上線（`00170-ruw`），過渡期新舊並存，所以每張卡可以各自上線、各自驗收。
  - 第 2 節（204 改 200）不開卡：`ApiClient` 只看 2xx。專案裡比對 `== 200` 的只有登入端點（`auth_service.dart:150`）和外部商店查詢，都不在那 8 支裡。
  - 論壇「有新回覆」改成整頁重載，不再自己組 cursor。這個只抓尾巴的做法是前端自己設計的，後端沒有要求。
  - 補做最低版本強制更新。平常最低版本留空，維持可略過的建議更新，只有遇到這類破壞性改動才調高。
  - 「我發起的活動」補上往下捲翻頁。
- 不開卡的配合事項（人工／溝通）：
  - 回覆後端更正認知：PR #93 只是可略過的提醒，而且 build 7 以前沒有這段程式；最低版本強制更新由 T-08 補上。
  - BUG-16：build 7 以前的 App 沒有任何提示機制，只能人工通知封測人員更新，並請後端確認前不要部署 BUG-16。
  - 移除舊寫法的條件改成：「含 T-01～T-08 的版本上架，並把 Remote Config 最低版本調到該版之後」。調好後通知後端。
  - 以後設最低版本時，iOS 一定要一併設 `update_url_ios`。

### T-08 低於最低版本的 App 被擋下並導去更新

**使用者價值**：遇到後端破壞性改動時，營運方可以把太舊的 App 擋下並引導更新，後端也能安全移除舊寫法。平常維持可略過的建議更新。
