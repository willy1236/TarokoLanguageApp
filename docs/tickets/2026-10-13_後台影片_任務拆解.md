# 2026-10-13 前端待辦（後台影片管理：上傳 YouTube 網址或 mp4／mov）任務拆解

來源：後端 repo `說明文件/前端交接/2026-10-13_後台影片_前端待辦.md`（決策紀錄 A54，規格 `docs/superpowers/specs/2026-10-13-admin-video-upload-design.md`，API `說明文件/API/內部管理.md` §6.2）。

## 現況與前提

- 技術棧：Flutter（`lib/`），手機 App 與網頁版同一份程式。後端已上線（主服務 `00255-fug`，PR #85），本次只動前端。
- 既有相關機制：
  - 後台入口 `lib/screens/admin/admin_home_screen.dart` 的 `_entries` 清單；畫面共用 `AdminScaffold`、`pushAdmin`、`handleAdminError`（`admin_widgets.dart`、`admin_error.dart`）。
  - API 呼叫集中在 `lib/services/admin_service.dart`（`ApiClient.get/post/patch`，列表回 `AdminPage<T>`＋`PageInfo`，`limit`＋`cursor`），模型在 `lib/models/admin_models.dart`。`ApiClient` 只打自家後端（`ApiConfig.baseUrl + path`），**沒有對外部網址送原始 `PUT` 的方法**。
  - 分類：`CategoryService`（`lib/services/category_service.dart`）提供快取與 `labelOf`；`AdminService.fetchCategories(CategoryModule)`。文章表單 `admin_article_form_screen.dart` 內嵌「下拉＋新增分類」（`_newCategoryOption`、`_typingNewCategory`、長度上限 `adminCategoryLabelMax`），**目前只在 `feat/categories` 分支，尚未合進 `master`**。
  - 部落欄位已有共用元件 `lib/shared/widgets/related_tribe_field.dart`（`RelatedTribeField`）、`tribe_picker_sheet.dart`。
  - 選檔：依賴裡只有 `image_picker`（`pickVideo` 只開相簿；iOS 端用 PHPicker、`preferredAssetRepresentationMode = Current`，拿得到原始檔不轉檔）。沒有 `file_picker`、沒有背景上傳套件。
  - 測試：`test/fixtures/api/*.json` 錄製回應、`test/contract/api_contract_test.dart` 對模型做契約測試、`test/screens/admin/` 畫面測試。
- 這次會動到的既有部位：`admin_home_screen.dart`（加入口）、`admin_service.dart`、`admin_models.dart`、`admin_article_form_screen.dart`（抽出分類欄位）、`core/constants/api.dart`（端點常數）、`pubspec.yaml`（`file_picker`、背景上傳套件）、iOS `Info.plist`／Android manifest（背景上傳時）。
- 已定案的技術前提：
  - 只有管理員看得到；手機與網頁都要做（A54）。
  - YouTube＝貼網址、mp4／mov＝選檔案；其他網址後端回 `INVALID_YOUTUBE_URL`。
  - 影片檔直傳雲端 `session_url`（GCS resumable）：分段 `PUT`＋`Content-Range`，每段為 `chunk_size_multiple`（256KiB）倍數，建議 8MB；中間段 `308`、最後一段 `200`／`201`；查進度送空內容＋`bytes */{總大小}`；工作階段一週有效；不可整檔讀進記憶體。
  - 上傳完成後影片仍是「處理中」，由後端轉檔後自動上架；處理中的影片靠下拉重整看狀態，不做自動輪詢。
  - 列表回應沒有分類 `label`，顯示名稱用 `CategoryService.labelOf(CategoryModule.videos, …)`。
  - 沒有內容的 `POST`（下架）要帶 `Content-Length: 0`；`http` 套件會自動帶，沿用 `ApiClient.post` 即可。
  - 這一輪做背景上傳（T-06）。
  - 手機能從相簿或「檔案」選影片（加 `file_picker`）。
  - 上傳由 App 層級的上傳服務執行，可以離開進度頁，影片管理列表看得到進度；一次只傳一支，上傳中再選檔會提示等目前這支傳完。
  - 網頁版重新整理後，重選同一個檔案（檔名與大小相符）就從斷點續傳。
  - 開工前提：`feat/categories` 先合進 `master`（T-01 要從那裡的文章表單抽元件）。

## 任務卡

### T-01 [共用] 後台影片資訊欄位：標題、說明、分類（含新增）、部落

**使用者價值**：T-03（YouTube 上架）、T-04（選檔上架）、T-07（編輯）填的是同一組欄位、同一套分類規則。先抽好，三張卡不會各寫一份；分類欄位同時從文章表單抽出，文章與影片的「新增分類」行為一致。

**範圍**
- 包含：從 `admin_article_form_screen.dart` 抽出分類欄位成共用元件；新增影片資訊欄位組（標題、說明、分類、部落）；文章表單改用抽出的分類欄位。
- 不包含：YouTube 預覽、選檔（T-03、T-04）；送出 API（各功能卡）。

**驗收條件**
- [ ] 文章表單的分類下拉、「＋新增分類」、新分類長度檢查、清單載入失敗重試，行為與抽出前相同（既有 `test/screens/admin/` 文章表單測試全過）
- [ ] 分類欄位給 `CategoryModule.videos` 時讀影音分類清單
- [ ] 影片資訊欄位：標題空白時顯示錯誤；說明超過 2000 字顯示錯誤；分類未選時顯示錯誤；部落可不選、可清除
- [ ] 帶入既有值（編輯模式）時各欄位顯示原值，分類值不在清單內時仍顯示其名稱

**實作設計**
- 前端：
  - `lib/screens/admin/widgets/admin_category_field.dart`：把文章表單內的分類狀態（清單載入、`_typingNewCategory`、`_newCategory`、`_selectedCategory`、`_isNewCategory`、錯誤文字）搬進元件；文章表單只保留取值。
  - `lib/screens/admin/widgets/admin_video_meta_fields.dart`：標題（必填，1～100）、說明（選填，≤2000）、`AdminCategoryField(module: videos)`、`RelatedTribeField`。
- 介面：
  - `AdminCategoryField({required CategoryModule module, String? initial, required AdminCategoryController controller})`；`controller.value → String?`（下拉選的值或新輸入的名稱，未選為 null）、`controller.isNew → bool`、`controller.validate() → String?`（錯誤文字）。
  - `AdminVideoMetaFields({AdminVideoMeta? initial, required AdminVideoMetaController controller, bool titleRequired = true})`；`controller.validate() → bool`（逐欄顯示錯誤）、`controller.value → AdminVideoMeta`。
  - `AdminVideoMeta { String? title; String? description; String category; int? tribeId; }`，`toJson()` 只輸出有值的欄位（`description`／`tribe_id` 清除時輸出 `null`，供 PATCH 用）。
  - `titleRequired` 給 T-03 用：YouTube 可嵌入影片的標題可留空由後端帶入。

**依賴**：無（但要 `feat/categories` 已合進 `master`）

**風險 / 待決**：分類新增後要 `CategoryService.fetch(videos, refresh: true)`，送出成功後由呼叫端觸發，元件不自己判斷。

**進度**：未完成

### T-04 管理員能選 mp4／mov 檔，看著進度條上傳完成

**使用者價值**：自家拍攝的影片管理員自己就能上架，手機與網頁都可以，不必把檔案交給工程師。

**範圍**
- 包含：上傳頁「選擇影片檔」來源（從相簿／從檔案）、前端格式與大小檢查、建立影片、App 層級上傳服務與分段上傳器、進度頁、列表上的上傳進度、Wi-Fi 提醒、網頁版 `File.slice`。
- 不包含：斷線後自動續傳與 App 重開接續（T-05）；背景上傳（T-06）。本卡上傳中途失敗時顯示「上傳中斷」並提供「重試」，重試即從頭查進度接著傳（同一個 `session_url`），不做持久化。

**驗收條件**
- [ ] 手機有「從相簿」「從檔案」兩個選檔按鈕，都只能選 mp4、mov；選了超過 2GB 的檔案在送出前就擋下並提示
- [ ] 標題必填；送出後進入進度頁，顯示進度條、已傳／總大小、剩餘大小
- [ ] 開始前提示「影片較大，建議使用 Wi-Fi」（手機才顯示）
- [ ] 上傳中離開進度頁仍繼續傳，影片管理列表上方顯示這支的進度，點它回到進度頁
- [ ] 已有一支在上傳時再選檔，提示等目前這支傳完
- [ ] 2GB 檔案上傳過程中 App 記憶體不隨檔案大小成長（手機實機觀察）
- [ ] 傳完顯示「上傳完成，轉檔需要幾分鐘，完成後會自動上架」，回列表看到這支為「處理中」
- [ ] 建立時 `502 UPLOAD_SESSION_FAILED` 提示稍後再試、停在上傳頁；`UNSUPPORTED_VIDEO_TYPE`、`VIDEO_TOO_LARGE` 有對應提示
- [ ] 網頁版（Chrome）可完成同樣流程

**實作設計**
- 後端：`POST /api/admin/videos { source: "upload", file_name, file_size, content_type, title, category, description?, tribe_id? }` 回 `201 { video, upload: { session_url, method, content_type, size, chunk_size_multiple } }`；之後對 `session_url` 分段 `PUT`。
- 前端：
  - 選檔：手機「從相簿」用 `image_picker.pickVideo`（PHPicker 原始檔），「從檔案」用 `file_picker`（`FileType.custom`、`allowedExtensions: ['mp4','mov']`）；網頁用 `<input type=file accept="video/mp4,video/quicktime">`（`package:web`）拿 `web.File`。副檔名決定 `content_type`（`.mp4`→`video/mp4`、`.mov`→`video/quicktime`）。
  - `AdminService.createUploadVideo(UploadFileInfo file, AdminVideoMeta meta) → ({AdminVideo video, UploadSession session})`。
  - 上傳器 `lib/services/video_upload/resumable_uploader.dart`，平台差異用條件匯入切兩個讀檔來源：`ChunkSource.io(path)`（`RandomAccessFile` 依位移讀一段）、`ChunkSource.web(web.File)`（`file.slice(start, end)` 再讀成位元組）。上傳用獨立 `http.Client`，不經 `ApiClient`（目標是雲端網址、不帶 App 的 token）。
  - 上傳服務 `lib/services/video_upload/video_upload_manager.dart`：App 層級單例，持有目前這一支的 `ResumableUploader`，以 `ValueNotifier<ActiveUpload?>` 對外提供狀態；頁面離開不影響上傳。
  - `lib/screens/admin/admin_video_upload_progress_screen.dart`：只訂閱 `VideoUploadManager` 的狀態；T-09 也推這頁。`admin_videos_screen.dart` 上方顯示進行中的上傳。
- 介面（T-05、T-06、T-09 使用）：
  - `VideoUploadManager.instance.start(AdminVideo, UploadSession, ChunkSource)`（已有上傳中時丟 `UploadBusy`）、`.active → ValueListenable<ActiveUpload?>`（`ActiveUpload { AdminVideo video; UploadProgress progress; UploadState state; }`，`state`＝`uploading`／`interrupted`／`done`）、`.retry()`、`.cancel()`。
  - `class UploadSession { Uri sessionUrl; int size; int chunkMultiple; }`
  - `ResumableUploader(UploadSession, ChunkSource, {int chunkSize = 8 MiB})`；`Stream<UploadProgress> start()`（`UploadProgress { int sent; int total; }`，完成時關閉、失敗時丟 `UploadInterrupted`／`UploadSessionExpired`）；`Future<int> queryOffset()`（送 `bytes */{size}`，`308` 依 `Range` 回下一個位元組、`200/201` 回 `size`，`404/410` 丟 `UploadSessionExpired`）；`cancel()`。
- 測試：上傳器用假 `http.Client` 測分段大小、`Content-Range`、`308`／`200` 處理、`queryOffset` 解析 `Range`。

**依賴**：T-03（上傳頁與來源切換外框）

**風險 / 待決**：
- `image_picker.pickVideo` 在 Android 會先把影片複製到 App 快取，2GB 需要等待與空間；選檔後顯示「準備檔案中」。
- 網頁版 `session_url` 跨網域：後端說明雲端已設 CORS，`308` 回應的 `Range` 標頭在瀏覽器讀不讀得到要實測；讀不到就改成每段成功後以本機累計位移為準，查進度只在中斷後使用。

**進度**：未完成

### T-05 上傳中斷後能從斷點續傳，App 重開也接得上

**使用者價值**：2GB 用 4G 要 10～30 分鐘，中途斷線或 App 被關不用整支重傳。

**範圍**
- 包含：斷線自動重試、本機記住未完成的上傳、下次打開影片管理時接續。
- 不包含：App 在背景時繼續傳（T-06）。

**驗收條件**
- [ ] 上傳中關掉網路再打開，進度頁自動從斷點接著傳，不從 0 開始
- [ ] 上傳中把 App 滑掉再打開「影片管理」，看到「有 1 支影片還沒傳完」，點「繼續上傳」從斷點接著傳
- [ ] 檔案已被刪除或搬走時提示並讓管理員改用「重新上傳」（T-09）或放棄
- [ ] 工作階段過期（超過一週）時提示改用重新上傳，並清掉本機紀錄
- [ ] 查進度回 `200`／`201` 時直接顯示上傳完成
- [ ] 網頁版：重新整理後影片管理顯示未完成的上傳，提示「請重新選擇同一個檔案」；檔名與大小相符就從斷點續傳，不符就擋下要求重選

**實作設計**
- 前端：
  - `lib/services/video_upload/pending_uploads.dart`：用 `shared_preferences` 存 `{ video_id, session_url, size, file_path, file_name, title, created_at }`（網頁版沒有 `file_path`），建立成功後寫入、完成或放棄時刪除。
  - `ResumableUploader.start()` 內遇到網路錯誤時指數退避重試（上限約 5 次），每次先 `queryOffset()` 再傳。
  - `admin_videos_screen.dart` 上方顯示未完成的上傳卡片；點繼續 → 手機檢查檔案存在且大小一致、網頁請管理員重選檔案並比對檔名與大小 → 交給 `VideoUploadManager.start` 並推 T-04 的進度頁。
  - App 啟動時不自動續傳，等管理員打開影片管理按繼續。

**依賴**：T-04（上傳器與進度頁）

**風險 / 待決**：iOS `image_picker` 回傳的是 App 暫存目錄的複本，系統可能清掉；持久化前把檔案複製到 App Support 目錄，完成後刪除。

**進度**：未完成

**依賴**：T-04

### T-06 手機切到別的 App 或鎖螢幕時上傳繼續進行

**使用者價值**：管理員按下上傳後可以把手機放著或去做別的事，不必盯著畫面 10～30 分鐘。

**範圍**
- 包含：iOS background `URLSession`、Android WorkManager 前景服務（含通知列進度）。
- 不包含：網頁版（瀏覽器分頁在背景仍會跑，不另做）。

**驗收條件**
- [ ] iOS：上傳中按 Home 或鎖螢幕 5 分鐘再回來，進度有前進
- [ ] Android：上傳中切走，通知列顯示上傳進度；完成時通知「上傳完成」
- [ ] 系統中止背景工作後，回到 App 仍可依 T-05 續傳

**實作設計**
- 前端：每段先寫成暫存檔，再交給背景上傳（iOS background session 只能從檔案上傳）。套件候選：`background_downloader`（支援 iOS URLSession、Android WorkManager、可自訂 `PUT` 與標頭），需確認能逐段帶 `Content-Range` 並讀到 `308` 的 `Range`；不行就寫平台通道。
- 邊界：新增 `UploadTransport` port，T-04 的 `http.Client` 實作為前景 adapter，本卡新增背景 adapter；`ResumableUploader` 改依賴 port。
- 設定：iOS `Info.plist` 背景模式、Android 前景服務權限與通知頻道。

**依賴**：T-05（續傳是背景被系統中止時的退路）

**風險 / 待決**：背景 session 的進度回報頻率與 Flutter 端重新連上的時機在兩平台不同，需實機驗證。

**進度**：未完成
