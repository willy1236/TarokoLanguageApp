## 現況與前提
- 技術棧：Flutter，所有請求走 `ApiClient`（`lib/core/network/api_client.dart`）；處置推播由 `FcmService._showModerationNotice`（`lib/services/fcm_service.dart`）處理；唯讀狀態是只存記憶體的 `accountLockController`（`lib/services/account_lock_controller.dart`）。
- 既有相關機制：
  - 暱稱就是 `video_nickname`。寫入走 `UserService.updateMe`／`completeProfile`，被後端擋下時兩處都已用 SnackBar 顯示後端 `message`。個人資料頁的 `ProfileRenameDialog` 在送出請求前就關閉。

  - `EventService.createEvent` 只回 `id`，回應裡的其他欄位被丟掉。
  - 「活動通知」頁（`event_notifications_screen.dart`）是「我有報名的活動」收到的提醒收件匣；部落新活動推播不會出現在這個清單。
  - 已有 `friend_code` 的 model：論壇作者（`forum_models.dart`）、論壇通知 actor、好友／邀請／封鎖（`friend_model.dart`）、私訊（`friend_message_model.dart`）、好友來電（`callerFriendCode`）。沒有的：隨機配對 `peer_nickname`（`video_call_model.dart`）、定向通話 `peer_*`、活動發起人與參加者。

- 已定案的技術前提：

  - 帳號解鎖推播為 `type: "moderation"`、`action: "account_unlocked"`，標題「帳號已恢復」；`mute_lifted` 照原本處理。

  - 暱稱錯誤改顯示在欄位下方。
  - 暱稱旁附好友碼末 4 碼：先做 API 已有 `friend_code` 的地方，缺的列清單請後端補。

## 任務卡

### T-01 使用者能在「活動通知」頁關閉部落活動推播

**使用者價值**：不想收到「你的部落有新活動」推播的人可以自己關掉，不必關掉整個 App 的通知。

**範圍**
- 包含：service、「活動通知」頁 AppBar 齒輪與設定底板、inspector raw 測試、fixture 與契約測試。
- 不包含：其他推播類型的開關（後端不提供關閉）。

**驗收條件**
- [x] 進「活動通知」頁不多打任何請求。
- [x] 點齒輪開底板時 `GET /api/me/notification-settings`，載入中顯示轉圈，開關反映後端值；首次使用為開啟。
- [ ] 切換開關立即反映並 `PATCH { "tribe_events": <bool> }`；失敗時開關復原並顯示 SnackBar。
- [x] `GET` 失敗時底板顯示錯誤與重試，不顯示假的預設值。
- [ ] 精簡模式字級與間距正確。
- [ ] 實機確認位置與操作是否符合預期。

**實作設計**
- 前端：
  - `ApiConfig` 新增 `meNotificationSettings = '/api/me/notification-settings'`。
  - 新增 `lib/services/notification_settings_service.dart`：`fetchTribeEvents()` 回 `bool`、`setTribeEvents(bool)` 回後端確認後的 `bool`。欄位缺少時當作 `true`。
  - `event_notifications_screen.dart` 的 AppBar `actions` 在「全部已讀」旁加齒輪，開一個底板，內含一列開關，文案「接收『你的部落有新活動』推播」，副標說明「活動提醒不受影響」。
  - 文字樣式用 `AppTypography` 的 `*Style()` 方法。
- 測試：`integration_test/api_inspector_test.dart` 加 `GET /api/me/notification-settings` 的 raw 測試，錄成 `test/fixtures/api/get_api_me_notification_settings.json`，並補契約測試。

**依賴**：無

**風險 / 待決**：錄 fixture 時模擬器會跳 Google 帳號選擇，開始錄前先提醒使用者在旁邊點帳號。

**進度**：部分完成（2026-09-29）
- commit：b218f9a、16d9bc9、ccd005e
- 未驗：儲存失敗改在底板內顯示「儲存失敗，請稍後再試」而非 SnackBar（頁面 SnackBar 會被底板蓋住），驗收條件待使用者決定是否更新；精簡模式字級、實機位置與操作

### T-03 帳號被解鎖的人不用重開 App 就恢復正常

**使用者價值**：管理員解鎖後，當事人馬上能發文、留言、傳訊息、通話，不會被前端的唯讀狀態繼續擋住。

**範圍**
- 包含：`account_unlocked` 推播處理、回前景時補查唯讀狀態。
- 不包含：`mute_lifted`（維持原本）。

**驗收條件**
- [ ] App 在前景收到、或從通知列點開 `account_unlocked`：顯示「帳號已恢復」對話框，解除唯讀，並重新 `GET /api/me`。
- [x] App 在背景收到但沒點開：回前景時若仍是唯讀，查一次 `GET /api/account/status`，狀態為 `active` 就解除唯讀。
- [x] 不是唯讀的帳號回前景時不多打請求。
- [x] 查狀態失敗時維持唯讀，不跳錯誤提示。

**實作設計**
- 前端：
  - `_showModerationNotice` 加一個分支：`data['action'] == 'account_unlocked'` 時 `accountLockController.setLocked(false)`，並 `unawaited(UserService.fetchMe(forceRefresh: true))`，其餘沿用既有對話框。
  - `AccountLockController` 新增 `refreshIfLocked()`：`locked` 為 false 直接返回；否則 `AccountService.fetchStatus()` 後 `setLocked(status.isLocked)`，錯誤吞掉。
  - `main.dart` 的 `didChangeAppLifecycleState`（resumed 分支，約第 331 行）呼叫 `accountLockController.refreshIfLocked()`。
- 測試：`test/services/account_lock_controller_test.dart` 補 `refreshIfLocked` 在未鎖、已鎖轉 active、查詢失敗三種情況。

**依賴**：無

**進度**：部分完成（2026-09-29）
- commit：dd11e5d、8277259
- 未驗：前景／點開 `account_unlocked` 顯示對話框與重抓 `/api/me` 需實機收推播驗證；回前景補查的接線（`main.dart`）未有自動測試
