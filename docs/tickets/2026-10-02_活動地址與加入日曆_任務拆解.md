# 2026-10-02 活動地址與加入日曆 任務拆解

來源：使用者需求（2026-10-02）。一、活動發布把「地點」「詳細地址」合併成一個地址欄位，並可用 Google 地圖選位置；二、使用者能把活動加入自己的日曆。前端在本 repo，後端異動在 `Truku_backend`。開工前待決已於 2026-10-02 拍板，寫進下方「已定案的技術前提」。

## 現況與前提

- 技術棧：Flutter（Android／iOS 為主，Web 已在 master 並部署到 Hosting），HTTP 走 `ApiClient`；後端 Node／Express（`Truku_backend/backend/routes/events.ts`）＋ PostgreSQL，migration 在 `Truku_backend/db/migrations/`（最新 `062_event_images.sql`）。
- 既有相關機制：
  - 建立與編輯共用 `EventComposeScreen`（`lib/screens/events/event_compose_screen.dart`）：`_buildLocationCard` 是「地點」輸入（`_location`），下方另一個 `_address` 是「詳細地址」，兩者各上限 200（`EventDraft.locationMax／addressMax`），`EventDraft.validate` 兩個都必填。
  - 後端 POST `/events` 五個必填：title／description／location／address／starts_at；PATCH 時 location、address 不可清空。DB `events.address` 為 `NOT NULL`。
  - `location` 被多處當「短名稱」使用：列表卡片 `event_cards.dart`（`e.location ?? '線上'`）、`event_search_screen.dart`、後端提醒推播內文 `地點:${location}`、部落通知、`events-list.ts`、`admin.ts`、`reportSnapshot.ts`。`address` 只出現在詳情頁 `_infoRow(Icons.map_outlined, '地址', …)`，純文字、不能點；model 註解寫「前端可一鍵導航」但沒有實作。
  - 平台判斷集中在 `lib/core/platform/platform_features.dart`（`isMobile` 等）。
  - 沒有任何地圖套件或 Maps API key；`url_launcher`、`share_plus` 已在依賴內。
  - `EventDetail` 有 `startsAt`、`endsAt`（舊資料可能為 null）、`description`、`effectiveStatus`。
- 這次會動到的既有部位：`lib/models/event_draft.dart`、`lib/models/event_model.dart`、`lib/services/event_service.dart`、`lib/screens/events/event_compose_screen.dart`、`lib/screens/events/widgets/event_detail_body.dart`、`lib/screens/events/widgets/event_cards.dart`、`lib/screens/events/event_search_screen.dart`、`lib/core/platform/platform_features.dart`、新增地圖選點畫面、`pubspec.yaml`、`android/app/src/main/AndroidManifest.xml`、`ios/Runner/AppDelegate.swift`／`Info.plist`、`web/index.html`；後端 `backend/routes/events.ts`、`events-list.ts`、`admin.ts`、`reportSnapshot.ts`、新 migration、`說明文件/API/` 對應文件。
- 已定案的技術前提：
  - 手機優先：Web 的支援用 `PlatformFeatures` 判斷另走分支，不得改變手機原有行為。不做 Windows。
  - 串新欄位前先用 `integration_test/api_inspector_test.dart` 錄原始格式再寫 model。
  - 地址合併：最終由後端把 `location` 改為選填、顯示改以 `address` 為主（T-04）；後端改好之前，前端只留一欄，送出時從地址自動截出短名稱放 `location`（T-01）。
  - 地圖選點後若手動改了地址文字，就清掉座標，導航改用文字搜尋，並提示可重新在地圖上選擇。
  - 地圖選點做 Android、iOS、Web。
  - 加入日曆：手機開系統日曆新增畫面（`add_2_calendar`），Web 開 Google Calendar 範本網址。
  - 任何看得到活動詳情的人都能加入日曆，不必先報名。
  - 活動改時間或取消後，不同步使用者日曆裡已加入的事件，靠既有的活動變更推播告知。可訂閱日曆評估後不做：需要新表與每人專屬 token、對外公開的未登入端點與撤銷機制，日曆 App 同步間隔數小時到一天，仍趕不上臨時異動，且會與一次性加入的事件重複。
  - Google Maps Platform 用現有 Firebase 專案對應的 Google Cloud 專案啟用並綁定帳單，設預算警示與每日配額上限；配額用完當天搜尋失效，退回手打。

## 任務卡

### T-01 發起人用單一「地址」欄位發布活動

**使用者價值**：發起人不用再分辨「地點」和「詳細地址」要各填什麼，填一次就能發布。

**範圍**
- 包含：建立與編輯頁合併成一個「地址」欄位、自動產生短名稱、詳情頁顯示、既有活動的相容顯示。
- 不包含：地圖選點與座標（T-02）；後端把 `location` 改選填（T-04）。

**驗收條件**
- [ ] 建立頁只有一個「地址」欄位，未填時送出顯示「請填寫地址」，超過 200 字擋下。
- [ ] 送出後詳情頁看得到完整地址，列表卡片與搜尋結果顯示截出的短名稱。
- [ ] 編輯既有活動（當初分開填地點與地址）時，欄位帶入的內容不會遺失任何一邊的資訊。
- [ ] 舊活動的詳情頁仍正常顯示地點與地址。
- [ ] 活動提醒推播的「地點:」一行仍有內容。

**實作設計**
- 資料：無
- 後端：無，`location` 與 `address` 照舊兩個都送。
- 前端：
  - `EventDraft`：對外只剩一個 `address` 輸入與 `addressMax`；`location` 由 draft 內部推得，`toJson` 仍送兩個鍵。`validate` 的必填與長度檢查合一。
  - 短名稱規則（純函式，放 `event_draft.dart` 並補單元測試）：有分隔符（空白、逗號、頓號）取最後一段；否則去掉開頭的縣市與鄉鎮市區前綴（如「花蓮縣秀林鄉」）；結果為空就用原文。T-02 從地圖選到 Google 地點時改用地點名稱，不套這條規則。
  - `EventComposeScreen`：拿掉 `_address` 那一欄，`_buildLocationCard` 改標題「地址」、提示文字改為可填門牌或描述（如「秀林鄉富世村 xx 號／部落活動中心」）。
  - 編輯舊活動：`location` 與 `address` 不同且 address 不包含 location 時，帶入 `"$location $address"`，確保儲存後不丟資訊。
  - `event_detail_body.dart`：`location` 與 `address` 相同或 `location` 被 `address` 包含時只顯示一列「地址」；否則維持兩列。

**依賴**：無

**風險 / 待決**：列表卡片寬度有限，短名稱仍可能過長，確認 `maxLines`／ellipsis 正常。

**進度**：未完成

### T-02 發起人能在 Google 地圖上選活動位置

**使用者價值**：部落活動常在沒有門牌的地方，發起人在地圖上點一下就能定位，參加者也能直接導航到正確位置。

**範圍**
- 包含：地圖選點畫面、地點搜尋、選完回填地址、儲存座標、詳情頁地址可點開地圖導航；Android、iOS、Web。
- 不包含：活動列表的地圖檢視、依距離搜尋。

**驗收條件**
- [ ] 地址欄旁有「在地圖上選擇」，開啟全螢幕地圖，預設置中於發起人目前位置（拒絕定位權限時置中於花蓮秀林鄉）。
- [ ] 可用搜尋框找地點，選結果後地圖移過去並放上大頭針；也可直接拖曳地圖調整大頭針。
- [ ] 按「使用這個位置」回到發布頁，地址欄填入該處地址，列表顯示的短名稱為 Google 地點名稱（沒有名稱時套 T-01 規則）。
- [ ] 選點後手動修改地址文字，座標被清除，欄位下顯示「已改為手動地址，可重新在地圖上選擇」。
- [ ] 發布後詳情頁點地址，開啟 Google 地圖（沒裝就開瀏覽器）並定位到選的座標；沒有座標的活動改用地址文字搜尋。
- [ ] 編輯活動時重新選點會更新座標。
- [ ] 網頁版同樣能開地圖、搜尋、選點；手機的發布流程與 master 行為一致。

**實作設計**
- 資料：migration `063_event_coordinates.sql`，`events` 加 `latitude DOUBLE PRECISION NULL`、`longitude DOUBLE PRECISION NULL`，兩者同時有值或同時為 null（CHECK）。
- 後端：
  - POST／PATCH 接受選填 `latitude`、`longitude`：必須成對、範圍 -90~90／-180~180，否則 400 `INVALID_REQUEST`；PATCH 送 null 為清除。
  - 詳情回傳兩個欄位；列表不必回。更新 `說明文件/API/` 活動文件。
- 前端：
  - 依賴：`google_maps_flutter`（含 Web 實作）、`geolocator`；地點搜尋走 Places API（New）的 Autocomplete＋Place Details，反向地理編碼走 Geocoding API。
  - 新畫面 `lib/screens/events/event_location_picker_screen.dart`：回傳 `({String name, String address, double lat, double lng})`；拖曳停止後反向地理編碼更新下方地址預覽。
  - `EventDraft` 加 `latitude`、`longitude`；地址欄文字與選點時回填的不同就清掉座標。
  - `EventDetail` 加 `latitude`、`longitude`；`event_detail_body.dart` 地址列可點，有座標開 `https://www.google.com/maps/search/?api=1&query=lat,lng`，沒座標用地址文字當 query，`url_launcher` external 模式。
  - 平台：Android `AndroidManifest.xml` 的 `com.google.android.geo.API_KEY`、iOS `AppDelegate.swift` 的 `GMSServices.provideAPIKey` 與定位權限說明、Web `web/index.html` 載入 Maps JS API。`PlatformFeatures` 加 `supportsMapPicker`（mobile＋web），Web 專屬的差異只在這個判斷之後。
- 邊界：新增 `PlacesService`（`lib/services/`）包住 Autocomplete、Details、反向地理編碼，畫面只拿到整理好的結果，日後換供應商只改這一層。Web 直接從瀏覽器呼叫 Places REST 可能遇到 CORS，屆時改用 Maps JS API 的 Places 程式庫，只動這一層。

**依賴**：T-01（選點結果要回填合併後的單一地址欄）

**風險 / 待決**：
- API key 依平台分開並限制（Android 套件名＋SHA-1、iOS bundle id、Web referrer 含 Hosting 網址與 localhost），Android SHA-1 要含 release 與 Play 簽章兩組。
- 搜尋框輸入要 debounce 並使用 session token，避免吃額度。

**進度**：未完成

### T-03 使用者能把活動加入自己的日曆

**使用者價值**：使用者在手機日曆就看得到活動時間地點，不用回 App 查，也能用日曆自己的提醒。

**範圍**
- 包含：詳情頁「加入日曆」按鈕、帶入標題／時間／地址／說明；手機與 Web。
- 不包含：活動異動後同步使用者日曆（不做，見已定案的技術前提）。

**驗收條件**
- [ ] 任何人看活動詳情都看得到「加入日曆」；已取消、已結束的活動不顯示。
- [ ] 手機上點擊後開啟系統日曆新增畫面，標題、開始與結束時間、地點、說明都已帶入，使用者確認後存進自己的日曆。
- [ ] 網頁版點擊後在新分頁開啟 Google Calendar 新增事件頁，內容同上。
- [ ] 時間與詳情頁一致，不因時區偏移。
- [ ] 舊活動沒有結束時間時，日曆事件以開始後 2 小時為結束。
- [ ] 說明欄附上活動在 App 內的識別文字，讓使用者從日曆回查。
- [ ] 使用者取消新增畫面不顯示錯誤；Android 沒有日曆 App 時改開 Google Calendar 網址。

**實作設計**
- 資料：無
- 後端：無
- 前端：
  - 依賴 `add_2_calendar`；iOS `Info.plist` 加 `NSCalendarsWriteOnlyAccessUsageDescription`（iOS 17+）與 `NSCalendarsUsageDescription`。
  - 新增 `lib/screens/events/widgets/add_to_calendar.dart`：收 `EventDetail`，手機呼叫 `Add2Calendar.addEvent2Cal`；`kIsWeb` 時開 `https://calendar.google.com/calendar/render?action=TEMPLATE&text=…&dates=…&location=…&details=…`（`dates` 用 UTC `yyyyMMddTHHmmssZ`）。
  - 按鈕放 `event_detail_body.dart` 時間列旁，或 `event_action_bar.dart`；位置待實作時看版面。

**依賴**：無

**進度**：未完成

### T-04 手打地址的活動不再顯示截出來的短名稱

**使用者價值**：截出來的短名稱有時不準，後端改為以地址為主後，列表與推播顯示的是發起人實際填的內容。

**範圍**
- 包含：後端 `location` 改選填、各處顯示改為「有 `location` 用它，沒有用 `address`」；前端手打時不再送 `location`，移除 T-01 的截取規則。
- 不包含：清理既有活動的 `location` 資料（舊資料照舊顯示）。

**驗收條件**
- [ ] 新版 App 手打地址發布的活動，列表、搜尋、提醒推播、部落通知都顯示完整地址。
- [ ] 從地圖選到 Google 地點的活動，列表仍顯示地點名稱。
- [ ] 舊版 App 照舊送兩個欄位仍能建立與編輯活動。
- [ ] 舊活動顯示不變。
- [ ] 後台與檢舉快照在 `location` 為空時顯示地址。

**實作設計**
- 資料：`events.location` 若有 NOT NULL 約束則移除（待確認，`app_schema_postgresql.sql` 與 migration）。
- 後端：
  - `events.ts` POST 的 `location` 改選填（有給仍檢查 1-200）；PATCH 允許 `location` 為 null／空字串清空。
  - 推播內文、部落通知、`events-list.ts`、`admin.ts`、`reportSnapshot.ts` 的顯示用 `COALESCE(location, address)` 或等價處理；列表回應的 `location` 欄位維持名稱不變，值改為合併後結果，舊版 App 不必更新。
  - 更新 `說明文件/API/` 活動文件。
- 前端：`EventDraft.toJson` 手打時 `location` 送 null，地圖選點時送地點名稱；刪除短名稱截取函式與其測試。顯示端不需改（後端已回合併值）。

**依賴**：T-01（前端收尾要改的是 T-01 的 draft 結構）

**風險 / 待決**：前端收尾要等後端部署上線才能合，否則新版 App 送 null 會被舊後端擋 400。

**進度**：未完成
